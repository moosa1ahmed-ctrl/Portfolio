ParkSense AI In Progress Personal project · Solo build Private repo, in development

Description

A B2B SaaS parking management platform aimed at two real problems at once: operators losing revenue to inefficient spot usage and theft, and drivers losing time hunting for a spot, especially in underground structures where most "smart" parking systems fail because of poor connectivity. The system is being built backend-first: a FastAPI service currently exposing in-memory CRUD endpoints for spots, sessions, and operators, ahead of full PostgreSQL integration. The core logic still to come is a reinforcement-learning spot-assignment engine (extending the Q-learning work from the Smart Parking project below) and a computer-vision ANPR pipeline for automatic plate recognition, both designed offline-first so the system keeps working when connectivity drops.

Why

Solo, ongoing personal project, started as much as a way to learn backend development from first principles as a genuine product concept worth pursuing further.

  • In-memory CRUD endpoints, ahead of full database integration

  • Planned: a computer-vision ANPR pipeline, built offline-first for poor-connectivity environments
Smart Parking: Optimization vs. Reinforcement Learning CP468 Artificial Intelligence · Team of 4 View Project

Description

The urban parking assignment problem, matching drivers to open spots efficiently, modeled as two different problems at once: a graph search task and a Markov Decision Process, to see how deterministic optimization stacks up against adaptive reinforcement learning on the exact same scenarios. The requirement was to solve parking assignment under 3 different constraint scenarios (limited availability, walking-distance limits) and evaluate both approaches on total cost, adaptability, and convergence speed. That was satisfied with two separate solvers built from scratch: Dijkstra's algorithm combined with hill climbing for the deterministic side, and a Q-learning agent for the adaptive side, run head-to-head across all 3 scenarios to produce a direct comparison.

Why

Course project for CP468 Artificial Intelligence, built with a 4-person team as a way to explore two different AI paradigms, search-based optimization and reinforcement learning, on the same real-world problem rather than in isolation.

Tools & concepts used

  • Python
  • Dijkstra's algorithm with hill climbing
  • From-scratch Q-learning agent
  • Simulations across 3 constraint scenarios (availability, walking-distance limits)
  • Evaluation on total cost, adaptability, and convergence
  • Co-authored an 8-page IEEE-format research paper with the team and presented findings to the class

Equipment Test Center, DBMS CP363 Database Systems · Team of 2 View Project

Description

Built to go through the complete database lifecycle for an equipment testing center rather than just writing isolated queries: ER/EER modeling of the real-world entities and relationships, translating that into a relational schema, then formally proving the result was properly normalized, and finally building a real application on top of it. The core logic lives in an 11-table schema with enforced primary/foreign key and CHECK constraints, plus subqueries, correlated subqueries, and window functions to support reporting-style queries, and views built on nested subqueries to simplify repeated access patterns. The requirement was a schema proven correct through formal normalization, satisfied by carrying it through to 3NF and BCNF, then a working Python CLI menu and Tkinter GUI were built on top so the database was actually usable, not just theoretically sound.

Why

Course project for CP363 Database Systems, built with a partner specifically to practice full database design, from modeling and normalization proofs through to a real interface, rather than working with a schema that was already handed to us.

Tools & concepts used

  • MySQL, Python, Tkinter
  • 11-table schema with enforced PK/FK and CHECK constraints
  • Subqueries, correlated subqueries, and window functions
  • Views with nested subqueries
  • Formal normalization to 3NF and BCNF
  • Python CLI menu and Tkinter GUI application on top

Digits of e, Digital Logic Circuit CP220 Digital Electronics · Individual project View Project

Description

A 4-bit combinational logic circuit that takes a binary input representing a decimal place (0 through 10) and outputs the corresponding digit of the mathematical constant e, with invalid inputs (11 through 15) correctly forced to output 0000. The core logic was derived the proper hardware-design way: a truth table was built for all 16 possible 4-bit inputs against the 4 output bits (O0-O3), each output was simplified using Karnaugh maps into a minimized Boolean SOP expression, and those expressions were then implemented as AND/OR/NOT gate networks. The requirement was for the circuit to correctly output the right digit of e for every valid input and cleanly reject invalid ones, satisfied by simulating the full gate-level circuit and testing it against all 16 input combinations before confirming it matched the truth table exactly.

Why

Individual project for CP 220 Digital Electronics, a hands-on exercise in carrying a problem all the way from a truth table to minimized, working hardware logic rather than stopping at the equations on paper.

Tools & concepts used

  • Truth tables
  • Karnaugh maps
  • Minimized Boolean (SOP) expressions
  • Maxima, used to algebraically verify each derived Boolean equation against the truth table before building anything
  • CircuitVerse, used to build the actual gate-level circuit and simulate it across all 16 input combinations, including proper handling of invalid states
